`ArrayFunction.original` is now transitive through any depth of wrapping a problem installs on its own functions, instead of stopping one level below, so it reaches through `EvaluationProblem.bind_functions()` rebuilding a wrapper past a previous run's. It still stops at a wrapper installed by a *different* problem, e.g. a sub-problem built on the functions of another one, and algebraic operations are not traversed either, so the original of a constraint offset by its value is that offset constraint.

A function output holding a `NaN` is now recorded in the history before the evaluation stops. The point an algorithm stopped at is therefore visible in the database, where it used to be evaluated, refused and left out of it. This concerns `stop_if_nan=True`, the default; a problem tolerating `NaN` recorded them already.

A design point holding a `NaN` now stops the evaluation of a problem keeping no database too. The input of a function is checked whether or not the evaluations are recorded, so a driver asking for no database, by passing `use_database=False` to `EvaluationProblem.bind_functions()`, is stopped before the user's function is called; such a point used to reach that function and to be evaluated, the input being checked on the path looking the database up only.

The perturbations of an approximated Jacobian no longer reach the history: they are evaluated by a callable that records nothing, so an approximated Jacobian adds one gradient entry to the database and no point. They are still taken in the coordinates the algorithm works in, normalized ones when it normalizes the design space, and each perturbed point goes through the map back to the coordinates the user declared before reaching the function, so an integer or discrete variable that is not relaxed keeps receiving integers and one that is relaxed is perturbed as a float.

A function declaring `with_normalized_inputs=True` is now refused by `EvaluationProblem.bind_functions()`, whatever the input space. The evaluations of a problem are recorded in the coordinates the input space declares and the half normalizing a point wraps the half recording it, so such a function can no longer be handed the normalized point it expects; it used to be refused over a space that cannot be normalized only, and to be silently evaluated at a point of the design space otherwise.

The augmented Lagrangian algorithms and `MultiStart` work on the problem as it is declared, whatever `normalize_design_space` asks for, as `ScipyLinprog` and `ScipyMILP` do. These libraries do not transform the problem they are handed: they delegate to sub-algorithms, which normalize the sub-problems according to their own settings, so the setting no longer has an effect at the top level. An augmented Lagrangian therefore evaluates the functions of the top-level problem, and approximates their Jacobian, in the coordinates the user declared: a finite-difference step is an absolute step instead of a step relative to the range of the variable, so the multipliers and the optimum a run returns move, in one direction or the other depending on that step and on the size of the design space. This concerns a run passing nothing, since the augmented Lagrangian settings default `normalize_design_space` to `True`; `MultiStart` defaults it to `False`, so there only a run passing `True` explicitly sees the setting dropped. Passing `normalize_design_space=True` explicitly to one of these libraries now logs a warning naming the setting and the library; a run leaving it at its default stays quiet, whatever that default is, and so does one passing `False` explicitly.

The driver settings `round_ints` and `skip_int_check` are replaced by `relax_integer_variables`, and their meaning changes: an algorithm that does not handle integer variables is no longer run on them by skipping the check and rounding the point at every evaluation, a rounding that no longer exists, but by relaxing them to float variables with the same bounds, so that the algorithm explores them continuously. The new setting `relax_discrete_variables` does the same for the discrete variables, whose relaxed value lies between their smallest and largest choices. Both default to `False`: such an algorithm raises a `ValueError` on a variable of a kind it does not handle unless that kind is relaxed, and relaxing is the only way to run it on such a variable, since the functions would otherwise receive values outside the declared domain. Code passing `skip_int_check=True` or `round_ints=True` has to drop them: nothing rounds the point at every evaluation any more, so a function needing integer inputs, such as a discipline whose grammar declares an integer, either rounds them itself under `relax_integer_variables=True` or is solved with an algorithm handling integer variables. A kind of variable the algorithm handles, e.g. the integer and discrete variables of a DOE, is left as declared whatever these settings ask for, since the algorithm, and the functions of the problem, such as a discipline whose grammar declares an integer, expect a value of the domain the user declared. An algorithm that does not transform the problem it is handed, such as an augmented Lagrangian, `ScipyLinprog` or `ScipyMILP`, relaxes nothing itself: it passes the variables on as declared, with a warning, and an augmented Lagrangian leaves the relaxation to the settings of its sub-algorithms. In a relaxed run, the functions and the database see relaxed values, `OptimizationResult.x_opt` is relaxed too, consistent with `f_opt`, the design space of the problem receives the projection of the optimum onto the declared domain, an integer one rounded and a discrete one snapped to its nearest choice, and `OptimizationResult.x_opt_projected`, `x_opt_projected_as_dict`, `f_opt_projected` and `is_feasible_projected` hold that projection, the design variables it is expressed with, the objective evaluated there and its feasibility, each falling back to its `x_opt`-side counterpart when the projection changes nothing, and `Database.to_dataset()` exports such a variable as a float column, decided from `Database.relaxed_variable_names`, the names a run relaxed, rather than from the values recorded, which may happen to be integral even for a relaxed run.

`DesignSpace.normalize_grad` and `DesignSpace.denormalize_grad` now return a gradient with the dtype it was passed with, where they used to cast it to the common dtype of the current value of the space, which is what a point of the space takes: a real gradient of a space holding complex values came back complex. `DesignSpace.denormalize_vect` keeps a complex value complex whatever the dtype of the current value, so a complex-step perturbation survives the map back.

The driver now also checks that the algorithm handles discrete variables, not only integer ones. The new `DriverDescription.handle_discrete_variables` field mirrors `handle_integer_variables`: an algorithm that does not handle discrete variables now raises a `ValueError` on one instead of silently relaxing it, unless `relax_discrete_variables` is `True`. SciPy MILP handles integer variables but not discrete ones. Among the SciPy global optimization algorithms, only `DIFFERENTIAL_EVOLUTION` handles integer variables, which it now keeps integral through SciPy's own `integrality` option instead of exploring them continuously; `DUAL_ANNEALING` and `SHGO` no longer declare handling them, so an integer variable now needs `relax_integer_variables=True` to be run with either of them. None of the three handles discrete variables. On the last release, all three declared handling integer variables and rounded them at each evaluation through `round_ints`.

`is_algorithm_suited` and `filter_adapted_algorithms` now take the integer and discrete variables of a problem into account: an algorithm that does not handle a kind of variable present in the problem is no longer reported as suited to it, relaxing being an opt-in choice made at execution and not something a description alone accounts for.
