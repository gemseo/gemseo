The protected (`_`-prefixed) ALL_CAPS class attributes are now named in lower snake case too, e.g. `_ATTR_NOT_TO_SERIALIZE` is now `_attr_not_to_serialize`, `_PACKAGE_NAMES` is now `_package_names`, `_CLASS` is now `_class` and `_RESULT_CLASS` is now `_result_class`. Like the public renames, the old names keep working with a `DeprecationWarning`, both when read and when a subclass body still assigns one, in which case the assignment is remapped to the new name; subclasses overriding these attributes should still be updated to use the new names.
For both the public and protected renames, the old name keeps working with a `DeprecationWarning` when read through the class or an instance, when written through an instance, and when assigned in a subclass body; but it is not aliased when assigned directly on the class itself, e.g. `SomeClass.OLD_NAME = value`. Such an assignment emits no warning and has no effect on the new attribute, which keeps its previous value; it also replaces the alias, so a later read of `OLD_NAME` returns the value that was assigned rather than the current value of the new attribute, and no longer warns either. This matters for the following class attributes, since assigning them directly on the class was previously a working, behaviour-changing operation: `OTGaussianProcessRegressor.MAX_SIZE_FOR_LAPACK` (now `max_size_for_lapack`), `OTGaussianProcessRegressor.HMATRIX_ASSEMBLY_EPSILON` (now `hmatrix_assembly_epsilon`) and `OTGaussianProcessRegressor.HMATRIX_RECOMPRESSION_EPSILON` (now `hmatrix_recompression_epsilon`); `BaseGrammar.DATA_CONVERTER_CLASS` (now `data_converter_class`); `Correlations.MAXIMUM_CORRELATION_COEFFICIENT` (now `maximum_correlation_coefficient`); `BaseDatasetPlot.DEFAULT_PLOT_ENGINE` (now `default_plot_engine`); `SobieskiProblem.USE_ORIGINAL_DESIGN_VARIABLES_ORDER` (now `use_original_design_variables_order`); `gemseo.core.discipline.base_discipline.BaseDiscipline.GRAMMAR_DIRECTORY` (now `grammar_directory`); and `CallableParallelExecution.MULTI_PROCESSING_START_METHOD` (now `multi_processing_start_method`). The design bound arrays of the Sobieski problem are now read-only: `SobieskiBase.design_bounds` and `SobieskiProblem.design_bounds` both return arrays with `writeable=False`. In-place mutation such as `problem.design_bounds[0][0] = 0.0` now raises `ValueError: assignment destination is read-only` where it silently succeeded before, and `lower_bound *= 2.0` raises `ValueError: output array is read-only`; callers needing a mutable array must copy it, e.g. `problem.design_bounds[0].copy()`. These properties return views, so the read-only flag cannot be re-enabled either: `problem.design_bounds[0].setflags(write=True)` raises `ValueError: cannot set WRITEABLE flag to True of this array`.
The initial state arrays of `gemseo.problem.ode.spring.springs_dynamics_discipline` are now read-only: the module-level constants `initial_time`, `initial_position` and `initial_velocity` all have `writeable=False`. In-place mutation such as `initial_time[0] = 1.0` now raises `ValueError: assignment destination is read-only` where it silently succeeded before, and `initial_time += 1.0` raises `ValueError: output array is read-only`. These three arrays are stored by reference in `SpringsDynamicsDiscipline.default_input_data`, so the default input data of a `SpringsDynamicsDiscipline` is read-only too: `discipline.default_input_data["time"][0] = 0.5` now raises `ValueError: assignment destination is read-only`. Callers needing mutable values must copy them, e.g. `initial_time.copy()`.
