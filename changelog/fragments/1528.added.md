The package `gemseo.space.transformation` defines the maps between a variable space and the space an algorithm works on: `BaseSpaceTransformation` is the contract, `SpaceComposition` composes transformations in order and is itself one, `SpaceNormalization` normalizes a design space, `SpaceRelaxation` relaxes its integer and discrete variables to float ones with the same bounds, so that an algorithm explores them continuously and the database is keyed on the relaxed values, its `project()` method mapping a value back to the declared domain, and `SpaceIdentity` is the neutral element. A transformation is built for a space, its `original_space`, and derives its `working_space` from it once, so that a transformation built on that working space can be checked against it: a `SpaceComposition` is given the factories of its transformations, such as their classes, and builds each transformation on the working space of the one before it, and `EvaluationProblem.create_working_problem()` refuses a transformation that is not built for the input space of the problem. The concrete classes are also reachable from `gemseo.space.transformation`.

`gemseo.core.function.base_problem_function.BaseProblemFunction` is the contract of the two halves a problem wraps each of its functions in: whether an evaluation stops on a `NaN`, whether the calls are counted and how many there have been, which lets a caller read them without knowing which half it holds.

`gemseo.core.function.evaluation_function.EvaluationFunction` binds a function to a database and a call counter, in the coordinates the user declared. It is the evaluation half of a problem evaluation: it looks up and stores the values, fires the new-point hook, counts the calls, computes an approximated Jacobian and stops a run on a `NaN`. A `None` database disables the lookup and the store, and nothing else. `EvaluationFunction.set_perturbation_transformation(transformation)` makes an approximated Jacobian perturb in the working coordinates of a transformation, each perturbed point being mapped back before reaching the function and the Jacobian before being recorded; `EvaluationProblem.create_working_problem()` calls it.

`Database.store_batch()` stores the values of a matrix of samples, one entry per sample, cutting the diagonal blocks of a block diagonal Jacobian matrix when asked to; it is what a vectorized evaluation records with.

`gemseo.core.function.transformed_input_function.TransformedInputFunction` adapts the argument of a function from the coordinates an algorithm works on to the ones the user declared, and its Jacobian by the chain rule. It is the adaptation half of the evaluation of a problem: it holds the transformation, and knows nothing of the problem, of its database or of its counters. It is built on an `EvaluationFunction`, which it wraps. The function itself is not transformed, only its argument. Stopping a run on a `NaN` is the business of the half it wraps; this one passes the setting on.

The global configuration setting `enable_working_database`, off by default, records the evaluations of a run a second time, in the coordinates the algorithm works on, and leaves them in the `working_database` of the problem. This is a debugging aid for someone wondering what an algorithm actually asked for: nothing of GEMSEO reads that store, and a run gives the same results whether it is enabled or not. It is independent of `use_database`, which names the database of the problem and nothing else, so a run recording nothing for the user can still record everything for the debugger. An algorithm building sub-problems and handing them to a sub-driver leaves it at `None`, working in the coordinates the user declared itself, and a parallel run records the evaluations of its own process only.

`EvaluationProblem.create_working_problem(transformation)` returns a **new** problem whose functions work in the coordinates an algorithm manipulates. The problem it is called on keeps its functions, its database and its input space, which stay the ones the user built; the database is shared rather than copied, since the history, the KKT checker and the progress bar read it while a run goes on. `EvaluationProblem.bind_functions()` binds the functions of a problem to its own database and counters, in the coordinates the user declared, and must be called before `create_working_problem()`, whose half is built on the one it installs. `create_working_problem()` sets `working_database`, kept afterwards as a debugging aid, and tells the evaluation halves of the functions the transformation, so an approximated Jacobian is perturbed in the coordinates the algorithm works in, and refuses a transformation not built for the input space of the problem; a `BaseDriverLibrary` run holds that map only while it lasts and releases it, whether the run succeeds or raises, once the run ends, so the user's own functions perturb in their own coordinates again afterwards.

`OptimizationResult` gains `x_opt_projected`, `x_opt_projected_as_dict`, `f_opt_projected` and `is_feasible_projected`: the optimum projected onto the domain the user declared, the design variable names bound to it, the objective evaluated there and its feasibility. They are copies of `x_opt`, `x_opt_as_dict`, `f_opt` and `is_feasible` when the projection changes nothing, e.g. a run that relaxed no variable; otherwise the driver evaluates the objective and the constraints of the user's problem at the projection, with the database switched off for that evaluation so `problem.database` stays aligned with `x_opt`, the evaluation still going through the same `NaN` check as any other and still counting as a call, and leaves `f_opt_projected` and `is_feasible_projected` at `None`, with a warning logged, when that evaluation raises.

`SpaceRelaxation.relaxed_names` reads the names of the variables the transformation relaxes to float ones, derived once, at construction, and read again to build the working space, so the two agree. `Database.relaxed_variable_names` is the set of input variable names a run relaxed, empty by default; a `BaseDriverLibrary` run replaces it with the names its `SpaceRelaxation`, if any, relaxes, emptying it when the run relaxes nothing, so `Database.to_dataset()` can decide the dtype of such a column from this flag rather than from the values recorded. It is cleared by `Database.clear()`, and merged, not overwritten, when an HDF file is read into a database, a file written before this attribute existed reading back as empty.

`Database.merge_function_histories(database, function_names)` stores into a database the history of some functions recorded in another one, e.g. the database of a sub-optimization, skipping a function the other database never evaluated, and carries over the names of the input variables its run relaxed.
