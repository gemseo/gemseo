A DOE can combine vectorization with normalization of the design space. The combination never worked: the vectorized evaluation path was unreachable because the normalized one took precedence, so the whole sample matrix was treated as a single normalized point. It was denormalized as a whole, the function was called once on it instead of once per sample, a single database entry was keyed on the matrix, and the evaluation counter recorded one call rather than one per sample. Requesting a Jacobian compounded it, since the normalization scales gradient columns by index and so reached only the first block of a block-diagonal Jacobian. A point and a Jacobian are now mapped to the coordinates the algorithm works on sample by sample, the diagonal blocks of the Jacobian of a batch being mapped in a single operation, so a vectorized run over a normalized space records what the same run records without either.

Normalizing a gradient carried by a densified legacy sparse matrix no longer raises. A driver declaring no support for a sparse Jacobian densifies the one a function returns, which yields a `numpy.matrix`, whose augmented assignments are matrix products rather than elementwise operations: scaling its columns raised a shape error over a space of more than one component. A DOE logged that failure and skipped the sample, so a run asking for the Jacobian of such a function over a normalized design space recorded no gradient at all.

Running a second algorithm on a problem already solved by a first one now honours the settings of the second: the functions are bound to the database again rather than reusing the wrappers of the first run. Before, the second run silently inherited the coordinates of the first, so a driver normalizing the design space after one that did not handed a normalized point to functions expecting a point of the design space, and the history recorded it as such.

An augmented Lagrangian no longer returns its starting point as the optimum when `normalize_design_space` is `False`. It used to wrap the functions of each sub-problem itself, in the coordinates its own setting asked for, and the sub-algorithm reused those wrappers instead of building its own; unless the two settings agreed, the sub-solver handed a normalized point to functions expecting a point of the design space, proposed no design better than the one it started from and the run stopped there. Each sub-problem is now handed to the sub-algorithm as it is declared, and bound and transformed according to the settings of that sub-algorithm.

`ScipyLinprog` and `ScipyMILP` no longer solve the wrong program over a design space that is not the unit box. They read the coefficients of the functions of the problem and hand the solver the bounds of its space, so the two have to describe the same space; these libraries therefore work on the problem as it is declared, whatever `normalize_design_space` asks for, which is what they already did before the functions of a problem were bound to it.

The history of an optimization problem no longer records a point no function was evaluated at: the database is keyed on the point the functions are evaluated at, the rounding of an integer component included. Over a space with integer variables, the history used to be keyed on the point before the rounding, e.g. an entry keyed on `7.3` for an evaluation at `7`. The problem logged at the start of a run, and the space it is defined over, are the ones the user built for the same reason.

Normalizing a gradient over a design space with integer variables no longer rounds its integer components. `DesignSpace.normalize_grad`, and `DesignSpace.denormalize_vect` without its lower bounds, scale a direction rather than a point of the space, so the rounding that snaps a point to the integer grid was destroying the components it was applied to, e.g. a gradient component worth 2.3 was reported as 2. A point is still rounded, a direction is not.

A vectorized evaluation recording a sparse Jacobian no longer raises. Such a run records the block of the Jacobian that belongs to each sample, and reading those blocks used to raise whatever format carried the matrix: the check for a `NaN` refused a sparse block, and a matrix in a format built for assembling rather than for reading, such as COO, DIA or BSR, cannot be read block by block at all. A sparse Jacobian is now left unchecked, exactly as on the non-vectorized path, where a driver declaring it supports one reads the matrix itself, and the blocks of such a format are cut from a CSR copy of it, the Jacobian handed back to that driver keeping the format the function returned.

A driver whose algorithm raises no longer leaves its hooks on the problem it was handed. It sets two of them on the recording layer of that problem for the duration of a run: a listener notified of each new iteration, and, on every function, the hook finalizing the previous iteration. Both used to be released only when the run finished, so an algorithm raising left them in place, keeping the driver alive through the functions of the user and firing them again on the next run.
